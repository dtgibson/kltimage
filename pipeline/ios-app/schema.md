# Schema — KLT Image for iPhone and iPad

## Path

Incremental (extending the shipped native data contract). The prior cumulative schema is `pipeline/custom-color-spaces-and-reusable-transforms/schema.md`, with the analysis-record and numerical contracts in its predecessors. This feature introduces an iOS app and an independent app-local method store. It does not introduce a database, backend, account, sync service, or a new portable document version.

## Current Schema State

### Shared scientific and document contracts

`KLTCore` is the canonical domain and processing module for both platforms. Its `DecodedImage` is one oriented first-frame, 8-bit premultiplied-sRGB RGBA source with an immutable pixel buffer, dimensions, alpha flag, source type, and the `KLTImage.AnalysisSource.v1\0` SHA-256 fingerprint over oriented dimensions and decoded bytes. The filename is descriptive and is excluded from that fingerprint. The source stays unchanged while the full frame receives the transform calculated from either the whole frame or one validated, top-left, half-open source-pixel rectangle.

The stable calculation vocabulary remains standard RGB and CIE Lab D65, the three shipped curated affine spaces, and validated user affine revisions. Covariance/correlation, `n - 1` accumulation, channel order and units, eigen ordering and signs, stability thresholds, limited-variation behavior, global RGB output range, Lab gamut clipping, premultiplied-byte rounding, and source alpha behavior remain the shared contract. Standard RGB and Lab calculation branches keep their existing operation order and golden pixels. A frozen recipe replays its captured working space, center, transform, inverse, and output mapping without deriving target statistics. Same-source replay retains byte identity with the originating calculated result.

The method library contains exactly two mutable artifact families: user working-space revisions and saved transform recipes. Standard and curated spaces are compiled into `KLTCore`, never stored or mutated. A working-space mathematical edit advances its definition version; a rename changes only library metadata. A recipe snapshots its method and origin and never follows later library edits. Its identity is a lowercase UUID and its mathematical bytes remain frozen. These are value types; neither platform resolves them through a remote identifier.

The existing portable documents are unchanged: `org.kltimage.working-space` version 1 (`.klt-space.json`), `org.kltimage.transform-recipe` version 1 (`.klt-transform.json`), and documentary `org.kltimage.analysis-record` version 1 for standard RGB/Lab calculations or version 2 for affine calculations and replay. All use the existing canonical UTF-8 JSON encoding, sorted keys, finite numbers, stable protocol strings, and one trailing newline. Method imports keep the 256 KiB maximum, depth and duplicate-key checks, exact fields, strict identity/version/semantic validation, and analysis-record rejection. The method-library store remains `org.kltimage.method-library` version 1 with only user spaces and saved recipes, sorted stable identities, unique names per section, validated timestamps, and a 16 MiB read limit. Future versions and corrupt content fail closed without rewrite.

The version-1 store shape stays `{schema, version, userWorkingSpaces[], savedTransforms[]}`. A user-space item stores `libraryName`, optional `purpose`, `createdAt`, `modifiedAt`, and a `definition` containing `{identity, definitionVersion, base, baseChannelOrder[3], baseChannelUnits[3], workingChannelNames[3], forwardMatrix[9], offset[3], inverseMatrix[9], outputBehavior}`. A saved-transform item stores `libraryName`, `createdAt`, `modifiedAt`, and a `recipe` containing `{identifier, recipeFormatVersion, algorithm, workingSpaceNameAtCapture, workingSpace, originSource, originatingAnalysis, frozenApplication, interpretation}`. The frozen application carries working center, row-major transform, output mapping, alpha policy, and byte quantization. Store arrays are sorted by stable identifier; identity is unique within each family, while normalized names are unique within each user section. Name normalization trims Unicode whitespace, applies canonical precomposition, then lowercases with `en_US_POSIX`. The portable method documents expose the same definition or recipe without store timestamps. Working-space coefficient/inverse/condition bounds and recipe finite-value validation remain exactly as specified in the previous schema.

The version-1 analysis document holds source fingerprint and dimensions, calculation request and region, channel conventions, calculated matrices/output mapping, and exploratory interpretation. Version 2 holds target source, tagged `calculated` or `replayed` execution, captured working-space definition, conventions, exactly one of calculation or replay, and interpretation. A replay document nests origin and frozen values under replay and never claims target-derived covariance or eigenvectors. Both versions are export-only and never become method inputs.

The accepted in-memory workspace is one source generation, immutable execution request, current processing job, and optional `CompletedEnhancement` containing pixels, applied method, and exactly one matching analysis-record snapshot. Image export and record inspection/export use that accepted snapshot and the same job-ID plus request-key currency gate. The import of a replacement image is provisional: the accepted workspace remains usable until the latest successful full decode commits. Neither source images, enhanced pixels, regions, records, comparison settings, ordinary analysis controls, nor file bookmarks persist across launches.

### Platform ownership after this feature

| Owner | Durable state | Responsibilities |
| --- | --- | --- |
| `KLTCore`, compiled for macOS and iOS | None | Scientific values, validation, deterministic codec bytes, image decode/analysis/replay/encode, source fingerprint, resource-limit preflight, and request acceptance rules. No AppKit, UIKit, PhotosUI, picker, or app-container URL dependency. |
| Existing `KLTImage` macOS app | Existing macOS Application Support `com.kltimage.mac/MethodLibrary/library.json` | AppKit panels, Mac workspace and library actor, Mac-specific writes and release path. Existing data stays in its container. |
| New iOS app target | Its own sandboxed Application Support `MethodLibrary/library.json` | Files/Photos acquisition, local method-library actor, transactional workspace, touch comparison, and explicit document/image export. Its store uses the same version-1 codec but has independent bytes and ownership. |

No cross-platform store migration or automatic transfer occurs. The user moves method documents explicitly. A missing iOS store means empty user sections; a corrupt, inconsistent, or future iOS store stays byte-unchanged, blocks user-library writes, and still permits standard/curated calculation.

## Changes in This Feature

### Added

- **Native iOS target and iOS tests.** Generate iOS/iPadOS 18-or-later app and test targets from `project.yml`, using the existing Swift 6 `KLTCore` sources as an iOS framework target or equivalent shared-source target. Preserve the macOS 14 target, identifiers, settings, tests, and release scripts. Keep platform adapters outside `KLTCore`; do not compile `KLTImage`'s AppKit model or views into iOS.
- **iOS import adapter.** Files uses a document picker for one supported local/provider image. Photos uses a system picker with current asset representation and requests a complete file representation, never a `UIImage`, thumbnail, or edited display preview as the analysis source. The provider file is kept in a temporary, app-owned location only for the pending import; security access and temporary data are released on success, failure, cancellation, or supersession. The shared pipeline gains a file-URL ImageIO path so iOS can inspect metadata and decode directly from the complete representation without loading a second full compressed `Data` copy. An unavailable, downscaled-only, or incomplete representation produces a recoverable error while the accepted workspace remains available.
- **Platform-specific resource policy.** Add an explicit, immutable decode limit argument (or an equivalent policy value) to shared preflight and decode. macOS callers keep the default 64,000,000 pixels and existing error copy; iOS callers pass 26,000,000 pixels and show the mobile-specific limit. Read ImageIO first-frame metadata and orientation, check positive, overflow-safe oriented dimensions and pixel count before full-resolution decode or app-owned frame allocation, then check actual decoded dimensions again. The same preflight applies to Files and Photos. Do not downsample, infer a higher limit from free memory, or change the mathematical image. The target size policy is separate from recipe-origin metadata validation: iOS may import a Mac recipe whose **origin** had more than 26 million pixels while still enforcing 26 million on the current **target** image.
- **iOS workspace model.** A main-actor model owns one accepted source, current effective request, one accepted completion, provisional import ID, processing job ID, and separate export IDs. Detached operations do decode, analysis/replay, record construction, and encoding. Replacement source commit is atomic only when its import ID is latest and successful. A successful replacement clears region and view position and selects whole-image sampling while retaining calculation choices. A changed effective source/method/matrix/sample/region invalidates the prior result and record immediately; a late job cannot publish. A frozen replay request carries the recipe snapshot and shows origin separately from target. Export captures the accepted result snapshot, rechecks currency before final write, and cannot write stale pixels or records.
- **iOS method-library actor.** Use the existing `MethodLibraryDocumentCodec` and `MethodLibrarySnapshot` in an iOS-local actor with a bundle-owned Application Support URL. Its transaction order is validate proposed full snapshot, encode, durable same-directory atomic replace, then publish. Preserve the current file and in-memory snapshot on failure. User-space and recipe import first produce a pending immutable value, then apply only an explicit conflict choice. Replace is same-type and non-downgrading; Import as Copy gives a new UUID; Cancel is mutation-free. The existing stable names, versions, and bytes are preserved when no copy or edit is requested.
- **iOS export adapters.** Encode the accepted full-resolution `EnhancedImage` with the existing PNG/TIFF/JPEG contract and `AnalysisRecordSnapshot` with its existing version router; export methods with the current codecs. Stage app-controlled output in a temporary file, complete encoding and sync, then hand it to a user-selected Files or share destination. Cancel and encode failure leave no final-named app-controlled file. A provider-owned destination may have different atomicity guarantees; report provider failure and retain the accepted workspace. Never save to Photos or upload automatically.
- **Transient touch geometry.** The single region remains integer source-pixel bounds and is the only analysis input. A shared viewport transform maps it to view coordinates for hit testing, handles, two-finger pinch zoom, pan, side-by-side, slider, rotation, and iPad resizing; view coordinates never become the stored region. Fit and accessible zoom controls change only that viewport. The divider has an independent reveal value. Active gesture ownership is explicit among region edit, divider, and canvas pan/zoom. Exact X/Y/width/height entry passes through the existing region validator. Comparison mode and layout are transient presentation state, not document fields.

### Modified

| Existing structure | Previous value | New value and reason | Risk and protection |
| --- | --- | --- | --- |
| `ImageProcessingLimits` / `ImagePipeline.decode` | One process-wide 64-million-pixel limit and Mac-specific message | A caller-supplied fixed policy selects 64 million on Mac or 26 million on iOS; the core still returns the same canonical decoded source. | An accidental default change could reject Mac fixtures or permit oversized iOS decode. Keep the old Mac overload/default and add boundary tests at 26,000,000 and 26,000,001 plus Mac 64-million behavior. |
| `KLTCore` Xcode target topology | Framework built for macOS only | Compile the same source contract for iOS as a separate platform product; use the same module API and golden fixtures. | Conditional source divergence could change bytes. Keep platform UI/file APIs out of core and run shared numerical/codec fixtures on both products. |
| Project stack description | Mac-only app | Record a native Mac plus iPhone/iPad stack with iOS 18 minimum, fixed mobile cap, and separate TestFlight path. | Configuration must not redirect the Mac GitHub release. Preserve its current deployment fields and add mobile details under `stack`. |

No production database column, relationship, index, document schema, store DTO, or shipped Mac store bytes change. The planned core API changes are source-compatible for existing Mac call sites. There is no automatic migration of macOS user methods into iOS storage.

### Unchanged

The first-frame oriented sRGB source and fingerprint, full-frame application, selected-region half-open geometry, all standard/curated/user working-space mathematics, covariance/correlation rules, recipe capture/replay, strict document limits, version-1 and version-2 analysis record encoders, Mac 64-million-pixel boundary, Mac Application Support store, and Mac GitHub/Developer ID release path remain binding. The iOS store reuses the *same* method-library schema and codecs; it does not share a physical file with macOS.

## Migration Plan

1. Make `KLTCore` compile on iOS by parameterizing the pixel cap and removing any platform assumptions from core build settings. Pin Mac golden images and JSON bytes before and after the change; add iOS fixture execution using the same immutable source and method inputs.
2. Add iOS app and test targets in `project.yml`, with iOS 18 deployment, distinct bundle identifiers, iPhone/iPad device families, Photos usage text only if required by the chosen picker API, and separate iOS signing settings. Regenerate the Xcode project. Keep Mac target settings and signed-release scripts untouched.
3. Add Files and Photos URL/file-representation import adapters with metadata preflight, cancellation, temporary-file cleanup, and the 26-million-pixel rejection before full decode. Verify orientation, color conversion, dimensions, and source fingerprint with each supported format.
4. Add an iOS-local version-1 library actor and durable file writer. On first launch, do not create a store; on first mutation, write its initial v1 snapshot atomically. A corrupt/future file remains in place for guided recovery. No data import from the Mac app container is attempted.
5. Build the iOS main-actor workspace around provisional import IDs and immutable job/request acceptance. Bind touch geometry and adaptive SwiftUI views to it. Add independent inspection and export adapters that consume only the accepted snapshot.
6. Verify both platform builds and cross-platform golden bytes, fixed-cap boundaries, cancellation, conflict transactions, fail-closed library recovery, and full-resolution exports. Exercise the complete workflow on the lowest-memory supported iPhone and iPad; if 26 million causes memory termination, record and implement one lower fixed iOS cap before release, with a PRD/architecture update and matching message/tests. Do not silently lower resolution per image.

## Design Decisions

- A separate iOS app target and app container provide native touch behavior without importing AppKit or leaking Mac file paths. `KLTCore` remains the only shared scientific and portable-document authority.
- The portable method document, not the app-local store file, is the cross-device exchange unit. This preserves explicit user control and avoids sync or data migration.
- The accepted completion is the sole source for pixels, inspector, and record/image export. View layout and gesture state cannot change scientific identity.
- The mobile cap is a fixed target policy, not a change to the Mac or recipe-origin contract. Preflight occurs before expensive allocation on both picker paths.
- TestFlight is the first iOS distribution channel. Signing and App Store Connect verification are independent of the Mac release artifacts and advertised GitHub channel.
