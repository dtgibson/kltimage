# PRD — Batch Processing
**Feature:** batch-processing  
**Date:** 2026-10-02  
**Stage:** 2 — The Planner  
**Source:** strategic-brief.md (approved)

## Feature Overview

Add a foreground batch workflow to KLT Image on Mac, iPhone, and iPad. Users select photographs, choose either independent whole-image calculation or unchanged replay of a saved transform, and explicitly save full-resolution results and optional analysis records to a chosen folder.

The approved strategy and user confirmation supersede the founding brief's historical exclusions of batch processing and mobile platforms. Other deferred product scope remains deferred. Requirements below resolve the strategy's resource, destination, and lifecycle decisions under the user's Autopilot instruction.

## User Stories

**US-01** — As an image analyst, I want to select a set of photographs and calculate each image independently with the same settings, so that I can explore the set without repeating the interactive workflow.

**US-02** — As a researcher with a saved transform, I want to apply its exact frozen mathematics to every selected photograph, so that target images do not change the method I chose.

**US-03** — As a Mac, iPhone, or iPad user, I want to review the inputs, method, output format, and destination before starting, so that exports are intentional and my original photographs remain safe.

**US-04** — As a user processing a mixed set of files, I want individual outcomes and actionable failures, so that I can identify the outputs actually saved and the inputs needing another attempt.

**US-05** — As a mobile user, I want cancellation and interruptions to preserve completed exports and explain unfinished work, so that I can stop safely without mistaking partial work for success.

**US-06** — As an analyst documenting a result, I want optional records tied to each exported image's exact source and method, so that its provenance remains reliable after library or workspace changes.

## Functional Requirements

### Entry, selection, and review

**FR-01** — The app shall provide a dedicated Batch workflow on Mac, iPhone, and iPad, available without an image in the interactive workspace. Entering, completing, failing, canceling, or dismissing a batch shall preserve the interactive source, accepted result and record, method, region, comparison, zoom, and pan. Batch execution shall neither create nor edit library entries. The app shall permit only one active batch and shall prevent concurrent interactive imports, calculations, or exports while the batch owns full-resolution processing; opening the workflow shall wait for an existing interactive operation to finish or be explicitly canceled.

**FR-02** — The app shall accept explicitly selected JPEG, PNG, TIFF, and HEIC inputs through native file selection on all platforms and native Photos selection on iPhone and iPad. It shall process the first image/frame using existing import behavior, require a complete supported representation, and reject unsupported items, folders, links, or nonregular file content with an item-specific reason. No selection shall grant permission to scan a folder or the Photos library.

**FR-03** — The app shall allow a setup containing 1–100 input entries, display “Up to 100 images per batch” at selection, and prevent selection from silently exceeding that limit. If a native selection returns more entries than remaining capacity, that addition shall be rejected with an explanation, preserving the existing list. The app shall preserve the returned selection order and append later selections; repeated selections shall remain separate, visibly numbered entries. Users shall be able to remove entries or clear the list before starting. Canceling a picker shall preserve the current setup.

**FR-04** — The app shall show a numbered input list with source display names and known selection errors, the count, execution mode and method, output format, optional-record setting, chosen destination, and proposed run-folder name before Start. It shall not require full-image decoding or acquisition of every source to populate this review. With no inputs, an unresolved mode/method, no destination, or active selection work, Start shall be disabled with a visible explanation. Known unsupported entries may remain in the list as failures; Start shall require at least one apparently eligible entry. Dimensions, availability, and decode validity not yet checked shall not be represented as verified.

### Resource and source boundaries

**FR-05** — The app shall acquire and process inputs sequentially, starting the next only after the current item's output decision and resource cleanup. Queued entries shall retain only bounded names, identifiers, and temporary access handles, not decoded pixels or eager copies of the full set. Native provider acquisition shall have at most one active source request. Late results from removed inputs, canceled selection, or an obsolete run shall be discarded and any app-owned files removed.

**FR-06** — The app shall enforce the existing maximum of 64,000,000 oriented pixels on Mac and 26,000,000 oriented pixels on iPhone/iPad before full decode and recheck decoded dimensions. Mobile inputs shall retain the existing 256 MiB encoded-file limit. Mac batch inputs shall have a 1 GiB encoded-file limit to bound stable source acquisition; this additional batch-only safeguard shall not change interactive import limits. Counts shall use actual acquired bytes rather than trust provider-reported sizes. Oversized, changed-during-acquisition, inaccessible, or malformed sources shall fail individually without downsampling, truncation, or substituting a thumbnail. These limits shall be available in setup and included in relevant failure messages.

**FR-07** — The app shall hold a stable source for the active item and use those same decoded source pixels for calculation/replay, the source fingerprint, and the exported record. It shall detect a source changing while being acquired and fail that item. Selection is not a promise to snapshot all source contents immediately: an item uses the complete source obtained when its turn begins. This distinction shall be explained in setup. Missing or revoked later sources shall fail individually.

**FR-08** — The app shall bound app-owned batch temporary storage to 2 GiB on Mac and 768 MiB on iPhone/iPad, including in-progress files. One item's encoded image shall be limited to 512 MiB on Mac or 256 MiB on iPhone/iPad, and its optional JSON to 1 MiB; reaching a cap shall cause a clear failure, never reduced resolution or quality. These ceilings leave room for the maximum staged source and one item's output material. The app shall not accumulate a local copy of all successful outputs. It shall release the current source, result, encoded output, and temporary files before acquiring the next source, retaining only the small outcome record. The preserved interactive workspace is separate from these batch-owned resources.

### Method choice and scientific behavior

**FR-09** — Each new setup shall default to “Calculate each image,” standard RGB, covariance, PNG, and analysis JSON off. The setup shall offer an explicit alternative, “Replay saved transform.” Switching modes shall show the corresponding settings and explanation; it shall never convert a working space into a frozen recipe or use an analysis record as executable input. Interactive selections shall not silently seed the batch or change these defaults.

**FR-10** — In calculation mode, the app shall allow any existing valid standard, curated, or user-defined working space and either covariance or correlation. Each item shall calculate from its own whole-image statistics and apply that calculation to its full image. Setup shall visibly state “Whole-image statistics”; region controls shall be absent and an interactive region shall never be inherited. The app shall explain that matching settings do not establish quantitative color comparability across independently fitted images. A valid limited-variation result shall retain existing identity/fallback behavior and be exported with its warning rather than reported as a processing failure.

**FR-11** — In replay mode, the app shall require selection of one valid saved transform from the existing local library. If none is available, it shall explain how to create or import one in the existing method workflow and prevent replay from starting. The recipe's captured working space, center, transform, output mapping, origin, sampling mode, and any original region shall remain unchanged for every target. The app shall expose the selected recipe's origin and explain that target statistics are not fitted; an original region describes the recipe's origin and shall not be imposed on targets, even when their dimensions differ. Matrix and sample controls shall not modify a replay recipe. Invalid or unsupported recipes shall block Start without falling back to calculation.

**FR-12** — On Start, the app shall freeze the run's ordered inputs, mode, complete method definition and names, output format, record setting, and destination. Later library renames, edits, deletions, workspace changes, and obsolete asynchronous completions shall not alter the accepted run or its records. Each accepted item result, its warning/diagnostics, record, and export authorization shall belong to the same run identity, item identity, source generation/fingerprint, immutable request, and processing job. A mismatched or obsolete result shall not be displayed as current or exported.

**FR-13** — For equivalent decoded source pixels and method settings, calculated and replayed batch results shall match the existing single-image operation exactly before lossy encoding. Processing shall retain existing orientation, 8-bit sRGB conversion, numerical stability, alpha, output mapping, and format behavior. Replay shall preserve existing per-target diagnostics while keeping captured recipe values unchanged. Neither mode shall pool statistics, normalize across the set, or transform an already enhanced result from an earlier item.

### Destination, naming, and artifacts

**FR-14** — The app shall require an explicit writable folder selection before Start: a native directory chooser on Mac and a native Files folder chooser on iPhone/iPad. The destination may be local or a user-selected provider-backed folder. The app shall display the selected folder's user-facing location, explain that a new run subfolder will contain results, and state that any provider upload/synchronization is controlled by that provider. Folder access shall last only for this setup/run and shall not create a persisted bookmark. Canceling destination selection shall preserve an earlier choice or leave Start disabled if none exists.

**FR-15** — On Start, the app shall create a new uniquely named run subfolder under the selected parent, using a readable name beginning `KLT Batch` and a date/time plus uniqueness suffix. It shall never reuse a prior run folder or replace an existing folder. Folder creation/access failure shall stop before any input processing, leave all inputs unprocessed, and offer a new destination/new attempt. Changing the destination after Start shall require ending the run and starting another. The app shall not silently fall back to app storage or a share sheet when a provider cannot support the required folder writes.

**FR-16** — Each item shall receive a safe filename comprising its stable three-digit queue number, a readable source stem, and `-klt`, followed by the selected format's normal extension; for example, `003-feather-klt.png`. Optional JSON shall use the same stem plus `-analysis.json`. Unsupported path separators, control characters, and path-navigation names shall be removed or replaced, stems shall fit destination filename limits, and an empty stem shall become `image`. A collision with either requested filename shall choose an unused suffix for both names. The app shall never overwrite an original, earlier output, unrelated file, or collision introduced between name selection and commit. The outcome shall show the actual final names.

**FR-17** — The app shall save one enhanced image per successful item in the run's selected PNG, TIFF, or JPEG format at the oriented source width and height. PNG and TIFF shall preserve existing alpha behavior. JPEG shall retain the existing 0.94 quality and opaque background behavior, with a visible notice that JPEG is lossy and does not preserve transparency. Selection of another format shall not change the scientific result. No source file or Photos asset shall be altered.

**FR-18** — When “Include analysis JSON” is off, the app shall write no analysis JSON. When on, it shall write one compatible documentary record alongside the exact image result for that item, using the existing version routing: standard calculated records retain version 1; nonstandard calculated and replayed records retain version 2. Names, source description/fingerprint, working-space revision, calculation or frozen recipe, and diagnostics shall describe the accepted item snapshot. Replayed records shall keep target and origin distinct and have no claimed target fit. JSON shall retain canonical existing encoding and shall not add batch fields, timestamps, paths, or a new schema. A record shall not be exported before its corresponding image commits.

**FR-19** — Each final artifact shall appear only as a complete encoded file; a failed write shall not leave a truncated image or JSON under its intended final name. The image and optional JSON are separately committed artifacts, not a promised cross-file transaction. An item shall count as successful only after every requested artifact commits. If the image commits but its requested JSON fails or is canceled, the app shall retain the image, mark the item partially saved, show the image's location and missing record, and exclude it from the successful count. It shall not delete already committed user output to simulate rollback. Temporary files shall never be reported as exports.

**FR-20** — The app shall check destination access and available capacity where the platform/provider exposes it before starting and before committing each item. It shall compare known capacity with the actual pending artifact bytes and a 64 MiB reserve, and stop before a write known to exhaust that reserve. An unavailable capacity estimate shall not be called verified; actual write failures shall remain authoritative. The app shall retain no second full batch of outputs for later delivery: committed user output is bounded by the 100-entry limit and per-artifact ceilings in FR-08. It shall not promise that selecting a destination reserves storage or that successful provider writes prove cloud synchronization.

### Execution, outcomes, and stopping

**FR-21** — During a run, the app shall show the frozen mode/method, destination/run folder, current source and index, current phase (acquiring, processing, or saving), settled-item count out of total, successful count, and separate failed/partial counts. It shall expose an outcome row for every input. Rows shall distinguish queued, active, saved, saved with warning, partially saved, failed, canceled, and not processed, with a concise reason and committed filenames where applicable. Progress shall not claim a percentage within a native operation that provides none.

**FR-22** — Item-specific acquisition, decoding, validation, numerical, encoding, or record-generation failures shall preserve prior outputs, mark that item's exact outcome, and continue to the next input. Insufficient source variation handled successfully by the current core is a warning, not a failed item. Destination permission loss, provider unavailability, inability to create/commit files, insufficient destination capacity, or an exhausted app-owned storage budget shall stop further items and writes, preserving known committed artifacts. The active item shall be failed or partially saved as appropriate; untouched remaining inputs shall be “Not processed,” with the shared stop reason. File-name collisions handled by FR-16 shall not alone stop a run.

**FR-23** — The app shall offer Cancel during acquisition, processing, and saving. Acceptance shall immediately disable further starts and show “Stopping…” while the active operation reaches a safe cancellation boundary. Queued items shall not start; they shall become “Not processed.” The active item shall become “Canceled” if no artifact committed, “Partially saved” if only its image committed and JSON was requested, or successful if all requested artifacts had already committed. A commit already in progress may finish; the app shall reconcile and report its actual outcome before leaving “Stopping…”. Late results shall not revive a stopped run. Already committed outputs shall remain available.

**FR-24** — The mobile workflow shall state before Start that KLT Image must remain open in the foreground. Entering the background during acquisition or execution shall initiate an interrupted stop with the same resource and commit rules as Cancel; returning to the foreground shall display the stopped outcome and shall not automatically resume. A transient inactive state while still foreground, such as a system picker or notification overlay, shall not itself discard setup or a run. If the OS terminates the process, the next launch shall show the normal workspace without pretending to restore or summarize the batch; completed files remain in the selected folder, app-container temporary files are cleaned automatically, and unresolved destination-local temporary files follow the explicit reselect flow in FR-27. No durable queue or guaranteed background completion is promised. On Mac, ordinary window focus changes shall not stop a run; closing the active batch surface or quitting shall be treated as a stop, with no automatic continuation after relaunch.

**FR-25** — A finished or stopped run shall show its mode/method, actual destination, total input count, successful count (including warnings), partial count, failed count, canceled count, and not-processed count, with every input represented exactly once. Only an all-successful run shall say “Batch complete.” All-attempted runs with failures shall say “Finished with errors”; user cancellation, interruption, and shared destination failure shall identify their stop reason. Partial outcomes shall distinguish “image saved; record missing” from no saved artifact. Rows and summary shall remain available in the current batch surface until dismissed or replaced, without keeping image buffers or persisting history.

**FR-26** — After a stopped or finished run, the app shall let the user return to setup for a new explicit attempt using the current list and choices while the surface remains open. It shall explain that starting again processes the listed inputs again into a new run folder; the user can remove already handled entries before starting. There shall be no hidden retry, automatic resume, destination reuse, or additional output on return to setup. A new Start shall capture a fresh request and revalidate access and the selected method. Dismissing the workflow shall discard the list/outcome and release access handles; reopening shall show the defaults in FR-09.

**FR-27** — The app shall remove only its own uncommitted batch temporary material after each item, a failed start, cancellation/interruption, and dismissal while the necessary access remains valid. On the next launch following abnormal termination, automatic cleanup shall cover app-container temporary files only. Destination-local temporary output shall be cleaned while its user-selected grant remains valid; after grant loss or relaunch, cleanup shall require the user to explicitly reselect the associated run folder. The app shall never silently reacquire access or persist a bookmark. It shall delete only verified owned temporary files in that folder and shall not delete inputs, provider-owned temporary originals, committed output, or unrelated files. Canceling reselect or selecting an unrelated folder shall delete nothing and leave unresolved storage reservations intact. If cleanup is prevented, the UI shall explain that temporary output remains, show the reserved bytes still counted against the temporary-storage bound, and offer safe folder reselect for cleanup. This reservation shall survive relaunch so another run cannot bypass the bound. A minimal private housekeeping receipt shall contain only a random ownership token, random temporary basenames without source names, and byte reservations; it shall contain no paths, source identities, methods, exported-output lists, queues, or outcome history. Reservations and their receipts shall be cleared only after owned temporary files are removed or their absence is verified in the associated reselected run folder. An empty run folder created by a failed start may be removed only while authorized, still empty, and known to belong to that run; a folder containing committed or unrelated files shall be retained.

## Non-Functional Requirements

**NFR-01 — Compatibility:** The feature shall support macOS 14+ and iOS/iPadOS 18+, with the same mode choice, scientific behavior, limits appropriate to the platform, and outcome semantics on Mac, iPhone, and iPad. Existing single-image import, comparison, regions, recipes, records, and export shall remain available with their current contracts.

**NFR-02 — Responsiveness:** Image acquisition, calculation/replay, and encoding shall not block native UI interaction. On the development Mac and local simulators, Cancel and navigation shall visibly acknowledge input within one second during a controlled long-running batch. Cancellation completion may wait for noninterruptible system decode, encode, or provider operations, but no next item or new artifact commit shall begin after the stop request.

**NFR-03 — Memory and performance:** Batch-owned full-resolution memory shall be bounded by one active source, one result, and its encoding/processing workspace, independent of queue length; settled rows shall retain no full-resolution image data. The existing Release-only 24-megapixel processing benchmark, including fingerprint/record overhead, shall remain below five seconds on the supported Apple-silicon development Mac. Batch throughput has no separate speed promise because acquisition and destination providers vary.

**NFR-04 — Accessibility:** All setup controls, input/outcome rows, modes, errors, progress, and Cancel shall have meaningful VoiceOver names and reading order. Essential status shall not rely on color. Mac keyboard users shall complete setup, start, cancel, and review results. Mobile layouts shall remain operable with supported large accessibility text sizes, and reduced-motion preferences shall be honored without hiding progress.

**NFR-05 — Privacy and access:** Processing shall remain local, with no app-added network transfer, analytics, library-wide Photos permission, persistent source/destination bookmarks, batch database, or implicit history. Native provider access shall be restricted to user selections and released when no longer needed. Private source and encoding staging shall remain inside the app container and excluded from backup. Complete-file publication may use clearly named temporary output files inside the explicitly selected run folder; these shall be disclosed as temporary, counted against the storage bound, and governed by FR-27 cleanup and ownership rules. The only persistent batch housekeeping shall be the minimal private, backup-excluded receipt permitted by FR-27, solely for unresolved temporary ownership and quota; it shall confer no external access and restore no run or outcome. User-selected cloud-provider destinations remain governed by the provider.

**NFR-06 — Reproducibility and trust:** Scientific core behavior and versioned JSON compatibility shall remain unchanged. Every exported image/record pair shall satisfy FR-12 ownership checks even during cancellation races, library changes, and a subsequent run. No retry or stale completion shall overwrite or misattribute any output.

**NFR-07 — Verification and delivery:** Verification shall use this development Mac and local iPhone/iPad simulators only; agents shall never enumerate, inspect, connect to, install on, launch on, or test on any physical device. Mac Debug and Release tests and relevant iOS simulator tests shall pass. Native provider behavior not reproducible in simulator and real-device TestFlight installation shall be explicitly labeled unverified and left to the user/testers. iOS delivery shall use TestFlight; Mac release shall retain existing signing, notarization, verification, and release requirements.

**NFR-08 — Review access:** Any development preview or design-review handoff shall be a verified HTTPS Tailscale URL restricted to the tailnet. No localhost, file URL, local path, or public-sharing requirement shall be presented as the user's means of reviewing the interface.

## Out of Scope

- Pooled statistics, calibration, automated color matching, quantitative cross-image claims, and new transform mathematics or working spaces.
- Per-image method overrides or regions, propagated interactive regions, and automated segmentation. A saved region-derived recipe remains valid for frozen replay.
- New import/export formats, source downsampling, increased image limits, tiled processing, parallel full-resolution items, recursive folders, watched folders, or command-line automation.
- A Photos output destination, replacement of originals, automatic sharing/publication, or a final share-sheet/ZIP bundle of accumulated outputs.
- Background processing guarantees, pause/resume, durable queues, retries across launch, persistent permissions, batch history/projects, or cloud synchronization supplied by the app.
- A comparison gallery, thumbnails required for every input, charts, aggregate reports, manifests, additional method exports, and batch-specific JSON schemas.
- Automatic retry of failed items or continuation in another destination. Users make a new explicit run using FR-26.
- Physical-device access by agents, public development previews, or a change to existing production approval and release-channel policy.

## Open Questions

None — all decisions are resolved in this document.

The 100-entry limit, additional 1 GiB Mac batch encoded-input cap, per-artifact/storage ceilings, direct folder destination, and foreground interruption policy are planning decisions within the approved bounded-workflow scope. The Architect owns their implementation, including native provider coordination and exclusive final-file publication. If a supported provider cannot fulfill the required write guarantees, it must fail visibly under FR-15/FR-22; it must not weaken no-overwrite or success semantics.
